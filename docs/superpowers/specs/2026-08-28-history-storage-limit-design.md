# 历史记录 500 MiB 上限设计

日期：2026-08-28

## 背景

`src/storage.rs` 将本机采集和 Gossip 收到的每份 `SystemMetrics` 完整序列化到
SQLite 的 `metrics_history.raw_json`。默认每 5 秒采集一次，Web 节点还会保存所有
对等节点的指标，因此节点数量增加时数据库增长很快。

现有清理任务每小时按 `storage.retention_hours`（默认 12 小时）删除过期记录。SQLite
默认删除记录后只把空闲页放入 freelist，数据库文件不会自动缩小；而且 12 小时内的
记录本身也可能超过可接受容量。因此保留时间不能构成磁盘容量上限。

## 目标

- SQLite 主数据库文件最大为 `500 * 1024 * 1024` 字节（500 MiB）。
- 达到容量上限时淘汰 `metrics_history` 中全局最旧的记录，继续保存最新指标。
- 升级后首次启动时，将已经超过上限的数据库收缩到限制内。
- 保留现有按 `retention_hours` 清理的行为。
- 不删除 `alerts_log` 和 `nodes_seen` 数据。

## 非目标

- 不增加用户可配置的容量参数；500 MiB 是固定安全上限。
- 不限制临时 rollback journal 文件的瞬时大小；限制对象是 SQLite 主数据库文件。
- 不改变指标采集频率、Gossip 协议、API 或 Web 展示。
- 不按节点分配配额，也不保证各节点保留相同数量的历史记录。
- 不在每次淘汰后执行 `VACUUM`；正常运行时复用 SQLite freelist，避免周期性全库重写。

## 容量定义

数据库容量按 SQLite 页计算：

```text
page_size * page_count
```

初始化每个连接时，根据实际 `page_size` 计算允许的 `max_page_count`，并设置
`PRAGMA max_page_count`。SQLite 在新增页会越过上限时返回 `SQLITE_FULL`，所以正常
运行期间主数据库文件不能超过 500 MiB。页数向下取整，实际硬上限不会大于目标字节数。

`max_page_count` 限制整个数据库文件，而淘汰对象只有 `metrics_history`。如果数据库中
已经没有历史指标可删，写入返回原始容量错误，不删除告警或节点信息，也不伪装成功。

## 数据库初始化与升级

`Database::new` 保持现有公开签名，并委托给接受字节上限的内部构造路径。生产代码传入
500 MiB；单元测试可传入较小上限，在临时 SQLite 文件上验证容量行为。

初始化顺序：

1. 建立连接池并运行现有建表语句。
2. 创建全局时间索引 `idx_metrics_time(timestamp, id)`，用于按时间定位最旧记录，也用于
   加速现有 `timestamp < cutoff` 清理。
3. 查询 `page_size`、`page_count` 和 `freelist_count`。
4. 如果主文件未超过 500 MiB，设置并核验 `max_page_count` 后继续启动。
5. 如果主文件已经超限，分批删除最旧指标，直到
   `(page_count - freelist_count) * page_size` 低于 450 MiB 安全水位。
6. 只在这一升级收缩路径执行一次 `VACUUM`，将 freelist 真正从文件中移除。
7. 重新设置并核验 `max_page_count`；如果文件仍然超过 500 MiB，则启动失败并返回明确
   错误，因为剩余非历史数据无法在不丢失受保护数据的前提下继续收缩。

450 MiB 水位为硬上限预留 10% 空间，避免升级收缩后立即再次触发淘汰。

## 满容量写入流程

`Database::store_metrics` 先执行现有插入。结果分三类：

1. 插入成功：直接返回。
2. 返回 `SQLITE_FULL`：按 `timestamp ASC, id ASC` 删除一批最旧指标，然后重试同一份
   新指标。
3. 返回其他错误：原样返回，不触发淘汰。

若一次淘汰仍不足以容纳新记录，继续按批次淘汰并重试；若已无记录可删，则返回最近一次
`SQLITE_FULL`。这样不会因锁冲突、损坏或 SQL 错误误删历史。

淘汰使用确定性顺序：时间相同时先删除较小的自增 `id`。每批操作是独立、短事务；SQLite
负责串行化并发写入。并发写入最多导致多淘汰一批旧记录，不会突破硬上限或删除新记录。

## 定时清理

`cleanup_old_metrics(retention_hours)` 保留现有公开行为和返回值，继续每小时删除超过保留
时间的记录。容量淘汰与时间清理彼此独立：哪个条件先满足，哪个先删除记录。

时间清理只产生可复用 freelist，不执行 `VACUUM`。因此数据库文件达到过高水位后可能保持
该大小，但在 `max_page_count` 下不会继续增长，并会优先复用空闲页。

## 日志与错误处理

- 启动收缩完成后记录删除数量及收缩后的字节数。
- 满容量淘汰时记录删除数量，便于确认节点进入容量治理状态。
- `SQLITE_FULL` 且无历史可删时保留错误链，由现有调用者输出存储失败日志。
- `VACUUM`、容量核验或 PRAGMA 执行失败时终止数据库初始化；不在未知容量状态下启动。

## 测试设计

测试放在 `src/storage.rs` 的现有模块内，使用 `tempfile` 创建真实 SQLite 文件，不 mock
SQLx 或文件系统。

1. **淘汰顺序**：写入多个时间和 `id` 不同的记录，调用批量淘汰，断言全局最旧记录先
   删除且最新记录保留。
2. **满容量继续写入**：用较小测试上限反复写入带有效 `SystemMetrics` 的大记录，断言
   最新写入成功、旧记录被淘汰、`page_size * page_count` 不超过测试上限。
3. **升级收缩**：先创建超过测试上限的数据库，再通过受限构造路径打开，断言执行收缩后
   文件页数不超过上限，且保留下来的记录是最新记录。
4. **无记录可淘汰**：构造由受保护表数据占满的数据库，断言写入返回容量错误且受保护数据
   不被删除。
5. **时间清理回归**：插入过期与未过期指标，断言 `cleanup_old_metrics` 仅删除过期记录并
   返回准确数量。

每个测试独立使用临时数据库，避免共享页大小、freelist 或连接状态。

## 修改范围

- `src/storage.rs`：容量常量、连接级页数上限、升级收缩、最旧记录淘汰、满容量重试及测试。
- `config.full.example.toml`：说明 Web 节点历史记录同时受 500 MiB 固定上限约束。
- `config.node.example.toml`：同步说明固定上限，避免两种发布配置产生不同认知。

`src/config.rs` 不新增字段，`src/main.rs` 不改调用方式，现有配置文件保持向后兼容。
